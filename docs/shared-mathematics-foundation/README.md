## Initial implementation through 49e0e1d

1. Working assessments now carry prospective `working-provenance@1`: question, competency, checker/version and whether reasoning was demonstrated, refuted or not established. The existing answer verdict remains separate. Replay rejects a changed binding; historical records remain readable without inventing new certificates.
2. `gradeRequestAsync` provides an asynchronous boundary before a decision is persisted. Experimental observations have a one-second deadline, retain their own identity/version, and explicitly carry `methodAuthority: false`. Neither positive entailment nor an experimental negative verdict changes answer credit or method evidence. The geometry Python checker remains disconnected from authoritative method grading; the async observer is an extension seam, not a claim of a live geometry adapter.
3. Generic method projection rejects cross-question/checker/domain bindings. Pre-provenance equation records remain historical-compatible. Fixtures representing those records explicitly omit the new field. A server label is not itself a signature: trust still comes from Django rejecting client decision fields and persisting its own immutable decision.
4. `mathematics-foundation@1` requirements select fresh questions for unobserved coverage, weak skills, failed-skill recovery and due-skill retention through existing module pools. Quarantine and grade constraints still apply. Choice/unsupported tasks cannot be selected to satisfy an impossible method requirement. Empty pools produce an honest unavailable result rather than mastery.
5. The existing slice can opt into requirements for linear equations, triangle properties, angle pairs and addition. The stock preview configures answer-evidence requirements (`method: false`); callers can explicitly require method evidence, and tests cover impossible method requirements stopping honestly. It does not label answer-only geometry as verified reasoning. Its ordinary teaching, investigation and recovery steps remain in charge; this policy does not declare existing generic explanations misconception-specific.
6. Re-entry requests are now checked on the server by replaying the existing engine using the validated learner, session, clock, events and educator acknowledgements. Invalid requests are rejected before an event is appended or an allowance consumed. This uses existing permissions and the existing pupil transaction lock.
7. Typed numeric working is preserved even when its notation or method is unsupported. Geometry can submit angle notation through the existing input. Non-equation symbolic answers retain their answer interpretation. Oversized working stays editable with a limit message instead of being silently truncated; working-only submissions can be saved unresolved by Django.
8. Paused/unavailable year modules offer one eligible existing lesson for review. The review is recorded as teaching; later answers in the same visit are marked assisted in both server handling and replay. Review itself awards no mastery. Unsupported working feedback preserves work, requests an intermediate step/rule and suggests supported lesson/practice.

## Limits at 49e0e1d

- No certified geometry method adapter is connected. The known alternative-proof false rejections and bare-conclusion semantics are isolated by conservative fallback, not repaired inside the Python reasoner.
- Targeted geometry explanations and new multi-step generators have not been authored. A pending diagnosed gap can still reach generic teaching; this slice does not certify teaching quality.
- The new requirements policy is preview-only and does not replace production competency status, statistical estimates or server retention policy.
- The async boundary preserves synchronous callers. The current Django grader entrypoint remains synchronous; observation callbacks are supplied by trusted code, not requests. A future Python adapter needs an explicit trusted task mapping and cancellation for its worker process.
- The legacy full mathematics typecheck has inherited errors. New diagnostics are compared against the pinned baseline without adding exclusions.

## Initial upward-progression boundary

The inspected production `goals.ts` overlay restricts challenges to the current curriculum and grade; `plan.ts` also works within the enrolled curriculum. That is an existing limitation, not the intended product boundary. Grade should place a learner initially, not cap their mathematical pathway.

The preview policy accepts `placement: "readiness"` for an explicitly chosen supported competency. For subsequent question selection it checks that competency's existing mandatory/plausible prerequisite evidence and then permits its questions above the enrolled grade through the same quarantine/module/exposure filters. Missing or overdue prerequisite evidence yields a preparation/probe requirement rather than claiming readiness. An ordinary selected target retains the current placement behavior. This does not automatically discover the next advanced target, invent engineering modules, or infer calculus readiness from one addition success. A goal-directed bridge sequence, application/representation evidence, and removal of the production goal overlay's grade constraints remain product work.

The local slice exposes that explicit readiness mode as `?foundation=1&placement=readiness&start=<supported-question-id>`. The explicit start question is displayed as a diagnostic challenge before the policy is attached; readiness governs subsequent selection, not access to that initial probe. This is a chosen-target preview, not an automatic cross-topic recommendation UI.
