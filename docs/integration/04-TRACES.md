## Persistence: what survives a new request / session

Round trip: the slice's own record events -> `POST /api/pupils/<id>/events/` (Django `checked_learning` re-decides every attempt with the trusted grader and stores the decision in the event body and the decision log) -> a NEW `APIClient` logs in again -> `GET .../events/` -> a NEW Node process rebuilds the learner with `learnerState`.

| Check | Result |
|---|---|
| attempts stored | 14 (same questions, responses, activities in the same order: True) |
| teaching (intervention) history | `teach` record stored and read back identically: True |
| server decisions | every attempt carries `grading-decision@1`, decidedBy server: True; server verdicts equal the in-page grader's: True |
| rebuilt evidence | status transfer, independent 9/12, retention scheduled |

Durable: attempt and teach records and decisions (Django `PupilEvent` + decision log). NOT durable and not claimed: the `SliceSession` trace, renderer frames and interaction events, and the in-memory clock. Evidence, hypotheses, the investigation decision, the teaching choice and the retention schedule are not stored. They are derived from the stored records on every read, and the derivation was shown to give the same result in a new process.

## Retention clock (the reported 9 November date)

The earlier report's due date of 2026-11-09 was wrong for the real clock. `SliceSession` then started at a hard-coded clock (2026-11-02T09:00Z) and advanced 60 s per step, so the date was 7 days after a fictitious 2026-11-02. It now defaults to the real clock.

With the real clock and the server's stored times: independent answer 2026-10-30T16:07:32.609892Z -> due 2026-11-06T16:07:32.609Z; due − independentAt = 7 days (`RETENTION_DAYS` = 7); due − now = 7 days. The in-memory run is a few minutes later (2026-10-30T16:14:26.722Z) only because its clock advances one minute per step, while the server stamps its own time. No scheduling event is written. The schedule (`retentionDueAt`, `retentionHistory` pending) is recomputed from the stored independent attempts, so it survives any new session exactly as the records do.
